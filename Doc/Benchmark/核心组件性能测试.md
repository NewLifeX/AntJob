# 核心组件性能测试

> 测试日期：2026-10-18 | BenchmarkDotNet 0.15.8 | Release

## 1. 性能概览

本次基准覆盖调度链路上每轮/每次任务都会执行的两类热点：**时间表达式与模板替换**（切片、SQL 模板展开）和 **SQL 片段解析**（SqlHandler/SqlMessage 执行前解析）。

核心结论：

- 已解析的时间表达式执行仅需 **35 ns**，模板替换优化后为 **379 ns**，均远低于一次调度周期（秒级），不构成瓶颈。
- 基准发现 `TemplateHelper` 使用区域性 `String.IndexOf(String)` 查找占位符，单次查找约 **2.4 µs**，比 `Ordinal` 慢约 **140 倍**。
- 改为 `Ordinal` 查找后，模板替换从 **23.3 µs → 379 ns（约 61 倍）**，消息模板从 **5.3 µs → 144 ns（约 37 倍）**。
- SQL 片段解析为纳秒级，线性随片段数增长（1 条约 404 ns，4 条约 1.4 µs）。

基准项目：[Benchmark/AntJob.Benchmarks](../../Benchmark/AntJob.Benchmarks)

- `TimeExpressionBenchmark`：解析并执行 `{dt+1M+5d:yyyyMMdd}`、复用已解析表达式、带格式化输出、`TemplateHelper.Build` 时间变量与消息变量替换，另设日期格式化与字符串查找对照组。

## 5. 核心指标

| 场景 | 单次耗时 | 单线程吞吐 |
|------|---------:|-----------:|
| 已解析时间表达式执行 | 35 ns | ≈ 28.6 M 次/秒 |
| 模板替换（时间变量） | 379 ns | ≈ 2.64 M 次/秒 |
| 模板替换（消息变量） | 144 ns | ≈ 6.94 M 次/秒 |
| SQL 片段解析（单条） | 404 ns | ≈ 2.48 M 次/秒 |
| SQL 片段解析（四条） | 1.41 µs | ≈ 707 K 次/秒 |

按作业步进 30 秒、单作业每步一次模板展开计算，上述组件的 CPU 占用可忽略不计。

## 6. 对比分析

- **纵向（优化前后）**：时间模板 23.3 µs → 379 ns（-98.4%）；消息模板 5.3 µs → 144 ns（-97.3%）；分配量不变（1328 B / 408 B），说明收益来自 CPU 而非内存。
- **横向（查找方式）**：区域性 `IndexOf(String)` 2.44 µs vs `Ordinal` 17.8 ns，相差约 137 倍；`TemplateHelper.Find` 每个占位符需要 2 次查找，直接放大了该差异。
- **表达式复用价值**：每次重新解析 206 ns，复用后 35 ns，省去约 83% 的耗时与 672 B 分配，符合“一次解析多次执行”的设计意图。

## 7. 性能瓶颈定位与优化建议

| 优先级 | 问题 | 现状 | 建议 | 预期收益 |
|:------:|------|------|------|----------|
| 已处理 | `TemplateHelper` 使用区域性 `IndexOf(String)` | 2.4 µs/次查找 | 改为 `StringComparison.Ordinal` 与字符重载 | 模板替换提升 37~61 倍 |
| 建议 | 模板键每次拼接 `"{" + key` | 每次查找产生短字符串 | 预置 `"{dt"`、`"{End"` 常量 | 进一步减少微分配（预估 <5%） |
| 观察 | 时间表达式每次任务重新解析 | 206 ns + 672 B | 按表达式字符串缓存 `TimeExpression` | 单作业每步省 170 ns 与 672 B |
| 观察 | SQL 片段解析每次执行 | 0.4~1.4 µs + 0.7~2.5 KB | 作业 SQL 未变化时缓存解析结果 | 高频小作业可省 30%~50% 解析开销 |

> 说明：本轮已按“已处理”项完成 `TemplateHelper` 优化（`Doc/架构设计.md` 记录），其余为可选优化，暂不实施。
